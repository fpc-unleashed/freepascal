# Technical Specification & Implementation Blueprint
## Project: Modernizing Pascal Generic Compilation via Witness-Based Lightweight Generics (WLG)

---

## 1. Introduction and Architectural Vision

The Free Pascal Compiler (FPC) has historically treated generics as compile-time syntax templates (macros). While this approach provides high execution performance through static monomorphization (duplicating code for every distinct type specialization), it introduces significant challenges: severe binary size inflation, high instruction-cache pressure, and prolonged compilation times.

The objective of **Witness-Based Lightweight Generics (WLG)** is to transition FPC to a hybrid compilation model. Under this model, the compiler generates a single, type-agnostic binary implementation for compatible type specializations. It achieves this by routing type-specific behaviors through an implicitly passed **Witness Table** (a static structure of metadata and function pointers) and grouping types into **Shape-Classes** based on their memory and ABI footprints.

By decoupling type checking from code generation, the `specialize` keyword is transformed from a "code-duplication instruction" into a "metadata-linking hint." This allows FPC to achieve binary sizes comparable to C# and Swift, while retaining the native, compilation-speed and dependency-free advantages of the Pascal language.

## 2. The Current Problem: Instantiation-Based Bloat

### 2.1 Monomorphization and Code Duplication
In FPC's current template-expansion architecture, when a unit contains:
```pascal
type
  TIntList = specialize TList<Integer>;
  TDoubleList = specialize TList<Double>;
  TPointerList = specialize TList<Pointer>;
```
the compiler parses the token buffer of `TList` three separate times, generating three distinct sets of assembly instructions for every method. If `TList` has 20 methods, the compiler emits 60 distinct procedures into the final binary, even though the structural logic of these methods (managing dynamic arrays, bounds checking, and pointer manipulation) is identical.

### 2.2 Compilation and Memory Footprint
Because specializations occur at the call-site inside client units:
1. **PPU Bloat:** The AST or token stream of the generic must be serialized into the `.ppu` file of the defining unit.
2. **Re-Compilation Overhead:** Every client unit compiling a specialization must parse, type-check, and optimize the generic methods from scratch.
3. **Instruction Cache (I-Cache) Eviction:** At runtime, the CPU is forced to load separate machine code blocks for `TList<Pointer>.Get` and `TList<TObject>.Get`, evicting hot instructions from the L1 cache despite identical binary instruction patterns.

## 3. Target Architecture: Witness-Based Lightweight Generics

The WLG model relies on three pillars: **Static Shape-Classes**, **The Witness Table**, and **Linker-Level COMDAT Deduplication**.

### 3.1 Shape-Classes (Layout-Based Groups)
Types are grouped into **Shape-Classes** according to how they are passed, copied, and disposed of at the ABI level:

*   **`Shape_Ref` (Pointer-Sized / Non-Managed):** Class instances, interface references, raw pointers, class references, and procedural pointers. These require no initialization or destruction.
*   **`Shape_POD_x` (Plain Old Data):** Types of static size $x$ containing no managed components (e.g., `Shape_POD_1` for `Byte`/`Boolean`, `Shape_POD_4` for `Integer`/`Single`, `Shape_POD_8` for `Int64`/`Double`). Copies are performed via raw memory moves; initialization and finalization are no-ops.
*   **`Shape_Managed` (Managed Value Types):** Types containing reference-counted or initialized components (`AnsiString`, `UnicodeString`, dynamic arrays, or records containing them). These require execution of runtime helper procedures (`fpc_copy`, `fpc_finalize`).
*   **`Shape_Complex_x` (Custom/Opaque Records):** Non-managed records of size $x$ with custom operator overloads.

### 3.2 The Witness Table Record Layout
The witness table is a static record generated by the compiler:

```pascal
PWitnessTable = ^TWitnessTable;
TWitnessTable = record
  Size: SizeInt;
  Alignment: SizeInt;
  TypeInfo: Pointer;
  Init: TWitnessInit;
  Copy: TWitnessCopy;
  Final: TWitnessFinal;
  Compare: TWitnessCompare;
end;
```

If a type is a POD type, `Init` and `Final` are set to `nil`.

## 5. Dynamic Stack Frame Generation

A major challenge when compiling shared generic methods is allocating local variables of type $T$ on the stack when the size of $T$ is not known at compile time.

WLG addresses this using **dynamic stack allocation**:

1. **Prologue:** Read the alignment and size of $T$ from the witness table, adjust stack pointer dynamically
2. **Stack Base:** NR_R12 holds the dynamic stack base (callee-saved)
3. **Local Variables:** Pre-populated with `localloc.reference.base = NR_R12`
4. **Initialization:** If `Witness^.Init` is not `nil`, call for each managed local
5. **Epilogue:** Call `Witness^.Final` for each managed local in reverse order
6. **Witness Preservation:** Copy witness pointer to NR_R13 (callee-saved) to survive Init/Final calls

## 6. Bootstrapping and Conditional Compilation Strategy

We use the conditional define `FPC_HAS_WITNESS_GENERICS`:

- All WLG-specific compiler and RTL changes are guarded by `{$IFDEF FPC_HAS_WITNESS_GENERICS}`
- If this define is absent, the compiler compiles to its exact, legacy state
- WLG is completely opt-in via `{$MODESWITCH LIGHTWEIGHTGENERICS}`

## 8. How to Use

```pascal
{$MODESWITCH LIGHTWEIGHTGENERICS}  // Enable WLG compilation
{$MODESWITCH -LIGHTWEIGHTGENERICS} // Disable WLG (use legacy monomorphization)
{$MONOMORPH}                       // Force monomorphization for performance-critical generics
```
