# Int128 / UInt128

Native 128-bit signed (`Int128`) and unsigned (`UInt128`) integer types that behave like any other ordinal - the same way `Int64` / `QWord` extend the 32-bit types. Literals, arithmetic, comparisons, `div` / `mod`, shifts, bitwise ops, `inc()` / `dec()` / `succ()` / `pred()`, `abs()` / `odd()` / `sqr()`, `for` loops, `case`, range / overflow checking, `Str()` / `Val()`, and `Write` / `Read` all work. Whenever the values fit 128 bits, these types replace a bignum library outright: no allocation, no unit, no wrapper type.

The types are always available on every native code target (and wasm32), in every mode. What the modeswitch `int128` actually gates is **integer literals wider than 64 bits** - it is enabled by default in `{$mode unleashed}`.

```pascal
{$mode unleashed}

var
  a: Int128;
  u: UInt128;
begin
  a := 170141183460469231731687303715884105727;    // high(Int128) = 2^127 - 1
  u := 340282366920938463463374607431768211455;    // high(UInt128) = 2^128 - 1
  writeln(a div 3, ' ', u shr 100);
end.
```

## Types and literals

| Type | Bits | Range |
|---|---|---|
| `Int128` | 128 | -2^127 .. 2^127 - 1 |
| `UInt128` | 128 | 0 .. 2^128 - 1 |

`low()` / `high()` on both types return the bounds as 128-bit constants. A literal of any base (decimal, `$` hex, `&` octal, `%` binary) that exceeds the 64-bit range carries the full 128-bit value under the switch. Without the switch an oversized literal keeps the historical real-constant fallback, so existing code is unaffected. The type names stay usable in `objfpc` / `delphi` - only the oversized literal needs the switch:

```pascal
{$mode objfpc}
{$modeswitch int128}

var a: Int128;
begin
  a := 100000000000000000000000000000000000000;   // 1e38 - the literal needs the switch
end.
```

## Arithmetic

`+`, `-`, `*`, `div`, `mod`, unary `-` operate on the full 128-bit value with two's-complement wraparound (there is no wider type to promote to):

```pascal
var a, b, c: Int128;
a := 10000000000000000000;        // 1e19, past high(Int64)
b := 10000000000000000000;
c := a*b;                         // 1e38, exact in 128 bits
```

`div` truncates toward zero and the sign of `mod` follows the dividend, matching `Int64`:

```pascal
a := -100;
writeln(a div 7);                 // -14
writeln(a mod 7);                 // -2
```

## Shifts and bitwise

`shl` / `shr` shift the full 128-bit payload; the count is taken mod 128. `shr` is a logical (zero-fill) shift on **both** types, as on the 64-bit types. `and`, `or`, `xor`, `not` operate on the full bit pattern:

```pascal
var u, v: UInt128;
u := 1;
u := u shl 100;                   // 2^100
writeln(u shr 100);               // 1

u := 18446744073709551615;        // low 64 bits set
v := u shl 64;                    // high 64 bits set
writeln(u or v);                  // 2^128 - 1
```

## Comparisons

`=`, `<>`, `<`, `<=`, `>`, `>=` compare `Int128` signed and `UInt128` unsigned, so the same bit pattern orders differently under the two types - all-bits-set is `-1` as `Int128` and `2^128 - 1` as `UInt128`.

## Conversions

Widening from any narrower integer is implicit. Narrowing back follows the usual truncation / range-check rules. Both types convert to `Double` (with the expected precision loss beyond 53 bits of magnitude).

## Hex literals sign-extend - the one real gotcha

A hex literal that fits `Int64` is parsed as a **signed** `Int64` and sign-extends when it lands in a 128-bit slot. This is the rule the language already applies elsewhere, but it surprises people writing bit masks:

```pascal
u := $ffffffffffffffff;           // 2^128 - 1 (sign-extended -1), NOT 2^64 - 1
u := 18446744073709551615;        // 2^64 - 1 - use decimal for the low-64 mask
```

The gotcha is not silent: assigning the hex form to a `UInt128` trips the constant range-check warning (`-1 must be between 0 and ...`), exactly as `QWord` warns on the 64-bit equivalent. The decimal form compiles clean.

## `Str()` / `Val()` / `Write()` / `Read()`

`Str()`, `Val()`, `Write(ln)`, and `Read(ln)` cover the full decimal range and signs. `Val()` reports the 1-based position of the first offending character in `code`, as for the other integer types. For the `$` / `&` / `%` bases a full 128-bit pattern is accepted into `Int128`, mirroring the smaller signed types:

```pascal
var a: Int128; s: string; code: integer;
a := 123456789012345678901234567890;
Str(a, s);                                             // '123456789012345678901234567890'
Val('-99999999999999999999999999999', a, code);        // code = 0
Val('$ffffffffffffffffffffffffffffffff', a, code);     // a = -1, code = 0
```

## `for`, `case`, `inc()` / `dec()` / `succ()` / `pred()`

All work, with surface behavior identical to the smaller ordinals. A 128-bit value does not fit one register, so these lower to equivalent forms: a `for` with a 128-bit counter becomes a `while`, an ordinal `case` on a 128-bit selector becomes an if-else chain, `inc()` / `dec()` / `succ()` / `pred()` become an add / subtract.

```pascal
for a := high(Int128)-2 to high(Int128) do
  inc(count); // runs 3 times

case a of
  1:                     s := 'one';
  100000000000000000000: s := 'match';
else
  s := 'none';
end;
```

## `abs()` / `odd()` / `sqr()`

Provided for both types. `abs(low(Int128))` wraps (its magnitude has no positive 128-bit representation), matching the other signed ordinals.

## Range and overflow checking

`-Cr` and `-Co` are honored: an out-of-range narrowing raises `ERangeError`, an operation that overflows 128 bits under `-Co` raises `EIntOverflow`. Without the switches arithmetic wraps silently.

## Not supported

- **Variant conversions**, in both directions - a `Variant` cannot carry a 128-bit value, so `v := a` / `a := v` is a compile error.

## Codegen and ABI

Not a bignum: on x86_64 a value lives in a pair of 64-bit registers and gets the treatment `Int64` gets on 32-bit CPUs. The cheap operations are inline instruction sequences, not calls:

- add / sub: `add`/`adc`, `sub`/`sbb` (also under `-Co`, via the CPU flags)
- and / or / xor / not: one instruction per half
- neg: `not`/`neg`/`sbb`
- compares: `cmp` on the high halves, then unsigned `cmp` on the low halves
- shifts: `shld`/`shrd` for constant counts, a `cl`-based double shift for variable counts
- mul: one `mul` for the low halves plus two `imul` cross terms
- 64 <-> 128 conversions: a `sar 63` or `xor` for the high half, no memory traffic
- range checks (`-Cr`) compare the pair in place

128-bit values are ordinary register variables - parameters, results, and loop-carried values stay in registers. Parameters travel in two GPRs (on SysV exactly the C `__int128` ABI, so `cdecl` interop matches gcc / clang) and results come back in `RAX:RDX`. Win64 uses the same register-pair convention as a private extension - MS defines no 128-bit integer, so `__int128` interop with mingw (which passes by reference) does not apply.

Only the genuinely large operations stay RTL helpers, mirroring `Int64` on i386: `div` / `mod` (schoolbook limb division for 64-bit divisors, a binary loop for wider ones), overflow-checked `mul` / `neg`, `Str()` / `Val()`, and the float conversions.

aarch64 gets the same register-pair treatment (`adds`/`adc`, `subs`/`sbc`, `negs`/`ngc`, jump-based compares, portable double shifts, parameters in two GPRs, results in `X0:X1` per the AAPCS64 16-byte-composite rule); `mul` stays a helper there. powerpc64 (with `addc`/`adde`, `subfc`/`subfe`), riscv64, loongarch64, mips64 (with `sltu` carries) and sparc64 (portable branch-based carry) inline the same operation set through the generic pair layer but keep parameters by reference for now. On every other CPU the helper model applies: operations lower to `fpc_*_int128` calls (the model gcc uses with `__divti3` and friends) and values pass by reference like a 16-byte record - down to the 8- and 16-bit targets. Constant folding uses the compiler's arbitrary-precision integer widened to the full 128-bit payload, so compile-time expressions match runtime results.

## Platform scope

Run-tested on x86_64 (win64 / linux64) and i386: arithmetic, `div` / `mod`, shifts, comparisons, conversions, `Str()` / `Val()`, `for` / `case`, and `-Cr` / `-Co` checking. Native register-pair codegen is compile-verified on aarch64, powerpc64, riscv64, sparc64, loongarch64, and mips64. The design does not need a 64-bit ALU - the helpers ride the same multi-word support `Int64` uses on smaller targets, and widening / range checks go word by word there.

## Demo

```pascal
program int128_demo;

{$mode unleashed}

begin
  // factorial climbs far past Int64 territory
  var f: UInt128 := 1;
  for var i := 2 to 34 do f *= i;
  writeln($'34! = {f}');

  // full-range literals and bounds
  writeln($'high(UInt128) = {high(UInt128)}');
  writeln($'high(Int128)  = {high(Int128)}');

  // 128-bit bit surgery
  var lo: UInt128 := 18446744073709551615; // 2^64 - 1
  var hi := lo shl 64;
  writeln($'lo or hi = {lo or hi}');

  // signed vs unsigned view of the same bits
  var s: Int128 := -1;
  writeln($'same bits: Int128 {s} vs UInt128 {UInt128(s)}');

  // Str / Val round trip
  var code: integer;
  var v: Int128;
  Val('-99999999999999999999999999999', v, code);
  writeln($'val: {v} (code {code})');
  {$ifdef WINDOWS}readln;{$endif}
end.
```

Output:

```
34! = 295232799039604140847618609643520000000
high(UInt128) = 340282366920938463463374607431768211455
high(Int128)  = 170141183460469231731687303715884105727
lo or hi = 340282366920938463463374607431768211455
same bits: Int128 -1 vs UInt128 340282366920938463463374607431768211455
val: -99999999999999999999999999999 (code 0)
```
